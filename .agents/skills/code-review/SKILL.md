# コードレビュー

共通規約と不変条件はルートの `AGENTS.md` を参照する。以下のパスはリポジトリルート基準。

## 範囲を合わせる

- 差分レビューは変更箇所と影響する呼び出し経路、事前調査は指定対象、全体監査はリポジトリ全体を対象とする。小さなレビューを自動的に全体監査へ広げない。
- レビューのみの依頼ではソースを修正しない。修正まで依頼されていれば、指摘を整理した上で範囲内の修正・回帰検証まで進める。
- `rg` / `rg --files` で既存実装、重複、呼び出し元、テストを調べる。特定の未提供検索ツールや他 Skill を前提にしない。

## 調査手順

1. ユーザー要求・差分から期待する変更と契約を確認する。設計判断の評価には対象の設計/ADR、設定依存の挙動には継承解決後の設定を読む。本番経路を評価するときは本番設定を使う。
2. エントリーポイントから入力・計算・監査・保存・発注まで、対象に関係する経路を追う。外部APIのマッピング変更なら `docs/api/` の該当仕様を照合する。
3. 機械的検証は対象に合わせ、既存 CI / `pyproject.toml` の lint・型・テスト設定を使う。全体監査・コード修正後の全体回帰は AGENTS.md に従う。存在しない補助スクリプトを呼んだり、レビューだけのためにソースを書き換えて PASS にしたりしない。
4. 以下の観点を検証し、指摘候補には最小再現条件と実害の根拠を付ける。
5. 指摘を反証する条件、同種の別実装、例外・部分失敗経路を再確認する。未確認の可能性を確定不具合にしない。

## 観点

- **優先**: 予測時点の情報可用性、当日行を除いた窓、基準期間分離、PIT、モデル/実効 exposure、NaN/Inf・共分散、cache / on-demand / flat、監査失敗の下流処理。
- **信頼性**: 入出力契約、空/境界値、例外の握り潰し、状態共有、部分書込み、再試行・冪等性、並行アクセス、終了期限、リソース回収。
- **外部境界**: 注文の重複、入力検証、認証情報・ログ、API仕様・設定マッピング。
- **保守性**: 実害のある重複・到達不能コード・過剰な抽象化、テスト不足、依存や環境差。好みだけのスタイル指摘は避ける。

必要な場合のみ、時系列/フォールバックは `leak-audit`、異常系は `edge-case-finder`、停止期限は `hang-prevention` の詳細を使う。

## 報告

指摘は重要度順に「ファイル・行 / 発生条件 / 実害 / 根拠 / 既存テストの不足 / 修正案」を示す。P0 は即時の重大障害、P1 は本番・主要機能の障害、P2 は限定条件の不具合、P3 は具体的な保守上の問題とする。件数を水増ししない。

確認範囲、実行した検証と結果、未確認・追加調査項目を残す。全体監査では観点別の確認状況とリリース可否（BLOCK / CONDITIONAL PASS / PASS）を付ける。差分レビューではその差分について結論を述べ、リポジトリ全体の健全性を保証しない。
