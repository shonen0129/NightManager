# データ・キャッシュの診断

`df_exec` の日付欠落、NaN、キャッシュの陳腐化や再構築の反復を調べるときに読む。パスはリポジトリルート基準。

## 欠落した段階を特定する

- 読込元は `src/leadlag/config/paths.py`、有効設定、実際の loader で解決する。旧 pickle が残っていても、その実行が SQLite とどちらを読んだかを確認する。
- raw データ → 前処理 → decision cache → バックテスト入力の行数・最終有効日・銘柄順・欠損率を比較し、日付が失われた段階を絞る。JP/US 休業日による対応と欠落を区別する。
- `src/leadlag/data/preprocessor.py::preprocess_data` の `strict_validation`、有効銘柄数、全列/一部欠損の分岐とログを確認する。「一銘柄の NaN で必ず全行が消える」という旧挙動を仮定しない。
- `is_provisional` の付いたターゲット・gap・open の代替値を確認する。未確定値のゼロ補完を実測リターンとして扱わず、下流で暫定行がどう処理されるかを追う。

## 鮮度判定と復旧

`src/leadlag/data/decision_cache.py::is_decision_cache_valid` は必要列・メタデータを検査し、全体キャッシュでは raw ETF との鮮度も比較する。双方の `updated_at` があればそれを使い、欠けるときは mtime を比較する。日付別キャッシュと全体キャッシュの検査を混同しない。

再取得・補間・再構築の前に、原因と下流への影響を特定し、再現に必要な旧入力・メタデータ・ログを保持する。更新が修正範囲に含まれる場合は対象データと期間を限定し、更新後の前処理とキャッシュ整合を確認する。mtime の調整、原因未確認の一括再取得、入力の書換えで症状を隠す操作を復旧としない。
