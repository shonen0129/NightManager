# 振る舞いを保つリファクタリング

共通規約・不変条件・検証範囲はルートの `AGENTS.md` に従う。以下のパスはリポジトリルート基準。

## 着手前

- `rg` で対象実装と既存の共通処理を探し、依頼が解決する構造上の問題を確認する。既に解決済みなら不要な変更を作らない。
- 呼び出し元・設定・保存形式・テスト・運用スクリプトへの影響を調べる。外部APIの対応に触れる場合は `docs/api/` の該当仕様を読む。
- 変更前の関連テストを実行し、比較用の入力・設定・出力を保持する。既存失敗は分離して記録する。独立した全体監査は全体監査を依頼された場合に行う。

## 実装と検証

1. 依頼範囲内で小さく分割し、関数契約、日付・銘柄順、キャッシュ境界、設定の不変性、監査・フォールバックを保持する。
2. 既存テストで保護されていない振る舞いには、必要な回帰ケースを先に追加する。実験パラメータや新機能を整理のついでに追加しない。
3. 変更前後を**別のコード版・別インスタンス・独立した設定コピー**で比較する。同じ model を2回呼ぶだけでは変更前後の比較にならない。
4. 実際の戻り値に合わせ、V2 の `PortfolioDecision.w_final`、scores、fallback、監査、必要なシグナル出力を比較する。キーは `src/leadlag/domain/portfolio.py` と対象関数で確認し、V1 固有の `predict_signals` キーを仮定しない。
5. 数値出力は原則一致させる。演算順変更により許容誤差が必要なら事前に根拠を決め、ランキング・ポジション・閾値判定が変わらないことも確認する。変更範囲に損益計算が含まれる場合は日次 gross/net・コストを比較する。
6. 対象の lint / 型チェックと AGENTS.md の全体回帰を行う。別途レビューを求められた場合や、契約維持に未解決の懸念がある場合は `code-review` を使う。バックテストを実行した場合は `backtest-report` に記録する。

## 完了

構造・公開API・設定・運用経路が変わった場合に該当ドキュメントを更新する。対象のロードマップ / ADR と整合を確認し、依頼範囲の完了と Phase 全体の完了を区別して報告する。研究コードの整理も依頼対象なら扱い、常に本番パスだけへ限定しない。
