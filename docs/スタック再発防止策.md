ADR の背景は `docs/decisions/2026-08-09-timeouts-and-transactional-cache.md`。タイムアウト定数を各所に重複定義しない。

### タイムアウトの限界

- `ThreadPoolExecutor` の with ブロックは worker の終了を待つ。`future.result(timeout=...)` の例外を捕捉するだけでは終了時に再び待ち続ける。例外は `TimeoutError` であり、`concurrent.futures.TimeoutExpired` ではない。
- 既存 `run_with_timeout` は daemon thread の join に期限を設ける。呼び出し側は戻れるが、処理自体は継続し得る。副作用を伴う操作のキャンセル・再送を保証しない。
- 強制停止が必要な処理は subprocess へ隔離し、対象プロセスグループに TERM、猶予後 KILL、終了回収まで行う。
- ツールの出力待ち時間は実行期限ではない。テストの1ケースごとの timeout もジョブ全体の期限と併用する。

## 3. 診断・復旧

1. **状態を保存する**: 対象コマンド、PID/親子関係、開始時刻・経過時間、最後のログ、処理中の日付や注文IDを確認する。macOS では `ps` / `sample`、Linux では利用可能なら `strace` 等を使う。調査対象を明確にする。
2. **待機理由を確認する**: 正常な時間待ち、ネットワーク、ロック、再試行、約定確認を区別する。cache のファイルがあるだけで古いロックと判定しない。
3. **停止が必要なら対象だけを停止する**: 自分が起動した処理または依頼で停止対象とされた処理へ TERM。期限内に終了しなければ対象を再確認して KILL。子プロセスの残存も調べる。一律の強制終了はしない。
4. **データを保護する**: lock ファイルの一括削除や SQLite の db / WAL / SHM の削除を復旧手順にしない。必要な修復は所有者・接続・整合性を確認して個別に行う。
5. **注文状態を照合する**: 注文送信後の timeout は失敗確定ではない。broker の注文・約定・建玉とローカル状態を照合し、二重注文を防ぐ。
6. **原因を解消して再実行する**: 元の依頼の範囲内で、停止期限を付けて再実行する。調査から本番注文へ切り替えたり、`--api-enable` を無条件に付けたりしない。
7. **結果を残す**: 停止原因・ガード・経過時間・終了コード・残存処理・再発確認を記録する。新しい原因が確認できた場合に本書の該当箇所を更新する。
