# 日次運用手順書

## 日米業種リードラグ市場中立戦略ファンド
**正式採用本番モデル:** Production Residual-BLPX-RA v2 (Residual-BLPX-RA v2)

本書は、日米業種リードラグ市場中立戦略ファンドの日次運用オペレーション、システム実行手順、安全監査基準、マニュアル・ロールバック手順、および監視・アラートのプロセスを定める実務マニュアルである。本書は『運用方針書』を補完する運用的詳細ドキュメントである。

## 1. 日次オペレーション手順

毎営業日、以下の手順に従ってシステムを実行し、注文発注およびポジション管理を行う。

### 1.1 米国市場クローズ後（日本時間早朝）の処理

1. **米国価格データの確定**
   米国市場クローズ後、当日の米国業種ETF15銘柄の終値を取得・確定させる。
2. **ターゲット残差化とデータの構築**
   過去60日のローリング OLS ベータに基づき、日本側ターゲットリターンを TOPIX 残差化した結合行列 $R^{\text{Residual-PCA}}_{\tau}$ を構築する。
3. **モデルの推定**
   直近250営業日のウィンドウに対して `winsor_sigma = 3.0` のウィンザライズを適用し、EWMA（半減期45営業日）で平均、標準偏差、相関行列を算出する。これをブロック分割し、正則化パラメータ $\alpha_{xx}=0.50, \alpha_{yx}=0.05, \alpha_{yy}=0.50$ を用いて $\Sigma_{XX}, \Sigma_{YX}, \Sigma_{YY}$ を算出する。
4. **BLPX予測行列およびシグナルの算出**
   Ridgeパラメータ $\rho=0.01$ を用いて基本予測行列 $B_{\text{blp}}$ を構成する。PCA正則化による $B_{\text{pca}}$、固定業種マッピング $M_{\text{sector}}$ による $B_{\text{sector}}$ を凸結合（$\lambda_{\text{pca}}=0.10, \lambda_{\text{sector}}=0.40$）して $B_{\text{struct}}$ を決定し、予測値 $\hat{z}_{J,t+1} = B_{\text{struct}} z_{U,t}$ を算出する。
5. **ギャップ調整済み予測分布の生成**
   朝 9:10 前に以下のスクリプトを実行し、当日の gap 調整済み予測平均 $\mu_{\text{gap},j,t}$ および共分散行列 $\Omega_{\text{gap},t}$ を算出する。
   * **実行スクリプト**: `tools/research/compute_gap_adjusted_distribution.py`
   * **出力先**: `var/live/pipeline_data/gap_adjusted_distribution/latest/matrices/` または SQLite `var/live/pipeline_data/gap_adjusted_distribution/gap_store.sqlite`
6. **リスク調整スコアの算出**
   スコア $\text{score}_{j,t} = \mu_{\text{gap},j,t} / \sigma_{\text{gap},j,t}$ を算出する。gap data が欠損している場合は、設定 `fallback.ondemand_fallback_enabled=true` のとき on-demand BLPX 計算を試みる。それでも失敗または無効の場合は **フラットポジション（$w_{\text{final}}=0$）** を返す。v1 フォールバックは 2026-07-09 に廃止された。

### 1.2 翌朝（日本市場寄付き前後）の処理

7. **目標ウェイトの決定（8:45〜9:00）**
   リスク調整スコアに基づき、上位5銘柄をロング、下位5銘柄をショートとして選定する。`baseline_style` 加重で基本ウェイト $w'_{j,t+1}$ を算出し、PIT 三分位ビニング（RuleD）により動的グロス乗数 $m_t \in \{0.75, 1.00\}$ を適用して、最終目標ウェイト $w_{j,t+1} = w'_{j,t+1} \times m_t$ を決定する。
   * **実行スクリプト（v2本番）**: `python3 -m leadlag.cli decision --config configs/production/production.yaml --gap-dir var/live/pipeline_data/gap_adjusted_distribution/gap_store.sqlite --api-enable --capital-from-wallet`
   * **本番設定ファイル**: `configs/production/production.yaml`（正本）
   * **主要出力ファイル**（`--live-dir` 配下、デフォルト `var/live/production_residual_blpx/`）:
     - `latest_weights.csv`: 当日の最終目標ウェイト
     - `production_scores.csv`: $\mu_{\text{gap}} / \sigma_{\text{gap}}$ スコア値
     - `pit_binning.json`: PITビニングのパーセンタイル・閾値情報
     - `production_audit.json`: 安全監査結果JSON
8. **自動安全監査（Safety Audit）の実行とフォールバック判断**
   目標ウェイトの算出と同時に、自動安全監査プログラムが走り、全監査項目を検証する（詳細は §2 参照）。監査が1項目でも失敗した場合、または致命的なデータ欠損が生じた場合は **フラットポジション（$w_{\text{final}}=0$）** を自動的に返す。2026-07-09 以降、v1 フォールバック・PCA-Ensemble フォールバックは廃止されている。
9. **リスク制限チェックと発注承認（9:00前）**
   ポートフォリオのネット／グロスエクスポージャー、参加率上限（ADVの10〜15%）をチェックする。グロスが200%（またはRuleDによる150%）の上限を超過している場合は、全銘柄ウェイトを同一比率で自動縮小する。VaR(99%)およびES(99%)が警戒水準を超過していないかを確認し、問題なければ発注を承認する。
10. **日本市場での発注・ポジション構築（9:10）**
    朝の寄付きから一定時間ノイズが落ち着いた「9:10」を基準時点として発注およびポジション構築を行う（gap_residualモードでは、9:00の寄付き価格確定後にギャップ補正シグナルを再計算し、9:10までに算出された最新シグナルに基づいて発注する）。

### 1.2.1 09:10 quote・実口座損失入力の必須条件

立花APIの現行ベースURLは v4r10 である（本番 `https://kabuka.e-shiten.jp/e_api_v4r10`、デモ `https://demo-kabuka.e-shiten.jp/e_api_v4r10`）。`TACHIBANA_API_URL` を環境変数で指定する場合も現行版を設定し、廃止済みv4r9を使わない。立花証券[公式APIページ](https://www.e-shiten.jp/e_api/)でリリース・廃止情報を確認する。

09:10の読み取り専用captureは起動ごとにプロジェクト `.env` を読み込むため、そこに設定された `TACHIBANA_API_URL` もv4r10であることを確認する。captureは廃止済みv4r9を送信前に拒否する。

ログイン応答が成功でも仮想URLが返らない場合、認証応答の `sKinsyouhouMidokuFlg=1` は交付書面が未読でAPIを利用できない状態を示す。標準Webサイトで書面を確認した後に次の定期captureで再確認する。フラグが0または応答にないまま仮想URLが欠ける場合もcaptureは停止し、認証応答全体や前日の価格で代替しない。

各capture attemptの認証診断は、capture出力先の `auth_diagnostics.jsonl` に `tachibana-login-diagnostics-v1` として追記する。保存対象はHTTP status、応答parse成否、`sCLMID` / `p_errno` / `sResultCode` / `sKinsyouhouMidokuFlg` のpresence・型・安全な値、4仮想URLの `absent/null/empty/nonempty`、復号試行・成否、停止段階だけとする。認証ID、第二暗証番号、秘密鍵、暗号化URL本文、復号URL、URL query、ログイン応答全体は保存しない。

実取引日のread-only/shadow受入前には `LEADLAG_SHADOW_ONLY=1 LEADLAG_CAPTURE_0910=1 .venv/bin/python tools/validation/check_readonly_acceptance_preflight.py --output var/shadow_runs/ml_overlay_value/microstructure/preflight.json` を実行し、実行SHA/dirty状態、v4r10 endpointのscheme/host/path、実効capture出力先、独立09:10 schedulerの登録状態とscheduler側capture pathとの一致を安全なJSONで記録する。認証情報やURL queryはpreflightへ保存しない。`status=BLOCKED` の場合は阻害checkを解消するまで定期captureを受入証拠として扱わない。

実行後は `.venv/bin/python tools/validation/build_readonly_shadow_acceptance_report.py --trade-date YYYY-MM-DD` で保存済みartifactを照合し、`reports/YYYYMMDD_readonly_shadow_acceptance/` の `report.json` / `report.md` を単一受入レポートとして使う。frozen、gap metadata、paired shadowのsnapshot IDが一致した場合だけmarket→shadowをPASSとし、実口座riskが欠落・不適格ならrisk込みStage 1はBLOCKEDのままにする。controlled liveのbroker side-effect reconciliationと通常scheduler一巡はこのレポートではDEFERREDとする。

actual-live decisionでは、`CLMMfdsGetMarketPrice`から取得したJP17銘柄とTOPIXの両側気配が全て揃い、09:10:00〜09:10:30 JST内に受信した場合だけquote snapshotを確定する。保存先は既定で `var/shadow_runs/ml_overlay_value/microstructure/frozen_YYYYMMDD.json`、変更時はcapture・gap生成・decisionの全てで `LEADLAG_CAPTURE_OUTPUT_DIR` を揃える。日付付きsnapshotは最初の有効データを不変保存し、gap生成とlive decisionは同じ `snapshot_id` を使う。quote不足、時刻外、破損、または当日snapshot不在なら実行は停止し、古い価格cache・前日終値への置換はしない。dry-runはこのlive必須条件の対象外。

実口座損失ガードは `var/live/pipeline_data/account_risk/latest.json`（任意の上書き先: `LEADLAG_ACCOUNT_RISK_SNAPSHOT`）から `account-risk-snapshot-v1` を読み込む。対象trade dateの直前セッションまでの損益、口座ID、実現・評価損益差分と観測済み費用の基準、cash・建玉・費用の完全照合が必要である。どれかが欠落・未照合・不一致、または日次/月次停止閾値超過の場合、新規エクスポージャーを停止する。既存ポジションの縮小・決済は既存のpost-decision制御に従う。現時点ではこの厳格な形式を出力する照合済みproducerが未実装のため、条件を満たすsnapshotが別途整備されるまでactual-liveの新規建ては fail-closed となる。立花の受入保証金を純損益として代用しない。

### 1.2.2 ML forward用の公式終値ラベル

凍結済み09:10 quoteに対応する大引け値は、翌日01:00 JST以降に立花 `CLMMfdsGetMarketPriceHistory` の当日 `pDPP`（終値）から取得できる。全JP17銘柄でtrade dateが一致する行がちょうど1件ずつある場合だけ、09:10 midpoint→公式終値のtargetを `var/shadow_runs/ml_overlay_value/outcomes.jsonl` に追記する。実行例は `.venv/bin/python tools/validation/collect_ml_overlay_forward_outcomes.py --trade-date YYYY-MM-DD`。これは読み取り専用の価格取得で、約定PnL・費用照合は作らない。同一日付・input digestのラベルは不変で、異なる値への上書きを拒否する。

ラベル取得後は `.venv/bin/python tools/validation/evaluate_ml_overlay_forward.py` でML on/offのpaired評価を生成する。shadow、frozen quote、公式closeが揃わない日は評価対象から欠損理由付きで残す。口座PnL・実約定費用の正本が未整備のため、candidateの実PnLや実費ベースの採否とは区別する。

### 1.3 日中から大引け決済までの処理

11. **ポジション・モニタリング（日中）**
    保有ポジションの評価損益、および相場急変・サーキットブレーカー発動等の異常事態をリアルタイムで監視する。
12. **大引け決済（15:00〜15:30）**
    大引けにかけてポジションの反対売買（決済注文）を行い、15:30までに全ポジションをスクエアにする。オーバーナイトでのポジション保有は原則禁止する。
13. **実績照合およびレポート更新（16:00以降）**
    約定結果と注文目標の照合を行い、日次実績レポートを作成する。アルファ減衰モニタリング指標（ローリングIR、シグナルIC、クロスマーケット相関）を更新し、データベースに保存する。

## 2. 自動安全監査（Safety Audit）基準

日次実行フローにおいて、`ComplianceAuditor` / `v2_auditor` が以下の観点を自動検証し、結果を `production_audit.json`、`leakage_audit.json`、`numerical_audit.json` に記録する。`all_passed` フラグが `true` でない場合、注文執行を自動停止し **フラットポジション（$w_{\text{final}}=0$）** を返す。

1. **ルックアヘッド・日付整合**
   シグナル算出日 `signal_date` が実際の取引実行日 `trade_date` より過去であることを確認。`us_res_beta_shift == 1` により US ベータ窓が 1 日シフトして当日を含まないことを保証する。
2. **残差化入力の整合**
   US/JP リターンの残差化が `all_returns_p4` / `jp_res_returns_p3` 経由で正しく行われ、P3/P4 一致条件を満たすことを検証する。
3. **アンサンブル重みの整合**
   複合モデルの重み和が 1.0 となることを検証する。
4. **シグナル・ウェイトの健全性**
   `signals` および `weights` に `NaN` / `Inf` が含まれていないことを検証する。
5. **市場中立制約**
   ポートフォリオの純エクスポージャーが `max_net_limit`（既定 0.051）以内、グロスエクスポージャーが `max_gross_limit`（既定 2.01）以内であることを検証する。
6. **コスト整合**
   `net_return = gross_return - cost` が数値的に整合していることを検証する。
7. **事前分布・残余化の妥当性**
   使用する事前分布 variant（`v2_raw` / `v1_raw` 等）および `V0_resid` / `C0_resid` の整合性を検証する。
8. **数値・リーク追加監査**
   `v2_auditor.run_leakage_audit` / `run_numerical_audit` により PIT ビニング、ターゲットリターン計算、相関ローリングの時間的方向性、残余化の漏洩を追加検証する。

## 3. 緊急停止および手動運用手順

システムバグ、APIの接続障害、データ欠損、または自動安全監査の失敗時には、以下の手順で新規ポジション構築を停止・是正する。

### 3.1 新規建ての即座な停止

1. **発注プロセスの停止**
   運用責任者の緊急承認のもと、ただちに `python3 -m leadlag.cli decision` の実行プロセスを停止する。すでに発注済みのポジションについては `python3 -m leadlag.cli close --api-enable` で反対売買によりスクエアにする。
2. **当日は手動スクエア**
   監査失敗や致命的データ欠損時、本番モデルは自動的に $w_{\text{final}}=0$ を返す。自動発注を利用しない場合は、当日の全ポジションを大引けまでに手動でスクエア（ネットエクスポージャー0）にする。
3. **原因調査と再開条件**
   ログ、`production_audit.json`、`leakage_audit.json`、`numerical_audit.json` を確認し、原因を特定する。`--dry-run` または `--api-dry-run` で再現テストを行い、監査が全 PASS してから `--api-enable` 運用に戻す。
4. **記録と報告**
   停止・是正の経緯を Git および運用日誌に記録し、投資委員会またはリスク管理責任者にインシデント報告書を提出する。

## 4. 監視および緊急対応（アラート）手順

システムは日次の損失状況を監視し、以下の閾値に達した場合は定められたアクションを自動的または手動で実行する。

actual-liveの注文判断で使う損失stopは、モデルreplay履歴と区別した照合済み実口座snapshotを要求する。上記snapshotを作成するproducerが未整備の間は新規建てが停止される。ここに記載する停止閾値の発火は新規リスク増加の停止を意味し、縮小・決済注文まで禁止するものではない。

### 4.1 損失アラート基準とアクション

* **日次損失が NAV比 1.5% を超過（`daily_loss_warning`）**
  * **アクション**: システムは運用担当者へ高優先度の警告アラート（メール・チャット）を出力する。ポジションの異常値や急激なファクターの傾きがないかを確認する。
* **日次損失が NAV比 2.5% を超過（`daily_loss_stop`）**
  * **アクション**: 緊急運用停止を発動する。システムによる新規建て注文の生成・発注を自動停止し、既存ポジションについては大引け（または市場流動性がある可能な限り速やかなタイミング）で強制決済を実行する。
* **月次累積損失が NAV比 5.0% を超過（`monthly_loss_stop`）**
  * **アクション**: 戦略の運用を一時停止する。投資委員会を招集し、戦略パラメータの再検証、市場レジームの変化の有無、および運用再開に向けた移行計画を決定する。

### 4.2 VaR・ES の限界値超過時の対応

日次で計算される 1日VaR(99%) または 1日ES(99%) が以下の閾値を超過した場合は、リスク管理責任者に即時エスカレーションを行う。

| 指標 | 警戒水準（ポジション縮小検討） | 停止水準（新規建て停止） |
|:---|:---:|:---:|
| 1日VaR(99%) | NAV比 2.0% | NAV比 3.0% |
| 1日ES(99%) | NAV比 2.5% | NAV比 4.0% |

リスク管理責任者は、一時的なボラティリティ急上昇によるものか、ポートフォリオの集中によるものかを分析し、PMに対してグロスエクスポージャーの引き下げ（例: 200%から150%への強制縮小）を指示する。
